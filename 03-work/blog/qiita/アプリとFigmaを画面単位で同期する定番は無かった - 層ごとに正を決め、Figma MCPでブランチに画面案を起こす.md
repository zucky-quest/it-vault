## TL;DR

- AI エージェントに、Figma へ新しい画面案を起こさせる仕組みを作りました。あわせて、Figma とアプリの見た目が食い違っていくのを防ぐ方法を調べました
- 調べた結論は、**アプリと Figma を画面単位で同期し続ける定番の方法は無い**、です。そこで、層ごとに何を正とするかを決めました。実装済みの画面はコードが正、デザイントークンは Figma のライブラリが正です
- トークンの正は、最初は逆に考えていました。デザインシステムの担当者に確かめると、Figma のライブラリが正でした。突き合わせのスクリプトで 117 件を比べ、対応する 100 件のうち**食い違いを 1 件**見つけています
- 画面案は、Figma 公式の MCP（`use_figma`）で、正本のファイルの**ブランチ**に起こします。`use_figma` は読み取り専用にできないので、**書き込む前にファイルを確かめ、ブランチ以外では止める**ようにしました
- 実データで動かして、部品が読み込めない、書体が書き換えられないなど、いくつも落とし穴を踏みました

## この記事の対象読者

- Figma とアプリの見た目のずれに悩んでいる方
- Figma の MCP で、AI エージェントに Figma を書かせたい方
- デザイナーがいない時間にも、画面案をチームで検討したい方

## 環境

- Figma（Organization プラン、Full seat）。Figma 公式の MCP サーバー
- Claude Code（スキルとして手順を持たせる）
- フロントエンドは React。デザイントークンは Tailwind 4 の `@theme` で CSS に定義

Figma の MCP の書き込みは、執筆時点でベータです。ベータの間は無料ですが、将来は従量課金になる予定です。挙動も変わりうるので、この記事は執筆時点のものとして読んでください。

## 背景：2 つの課題

課題は 2 つありました。

1. **画面案を Figma に起こす作業が、デザイナーに依存していた。** デザイナーがいない間は、新しい画面案をチームで検討できません
2. **Figma とアプリの見た目が、少しずつ食い違っていく。** 食い違いを見つける仕組みも、実装済みの画面を Figma 側で最新に保つ責任者もいませんでした

前の記事では、Figma を**読む**側の話を書きました（[デザインの在りかをリポジトリに書くと、AI エージェントが Figma まで辿れる](https://qiita.com/zucky-quest/items/d65e03e298c9e636160f)）。今回は、Figma に**書く**側の話です。

## 調べた結果、画面単位で同期し続ける定番は無かった

まず、食い違いを防ぐ方法を調べました。

| 方法 | 評価 |
| --- | --- |
| 画面単位で、双方向に同期し続ける | 定番の方法が無い。維持のコストに見合わず、一般には行わない |
| トークンの同期（Figma の Variables とコード。Tokens Studio、Style Dictionary など） | 最も整った定番。ただし Figma 側のライブラリの運用を変える必要があり、自分のチームだけでは入れられない |
| コンポーネントの対応づけ（Figma 公式の Code Connect） | 定番。プランの条件は満たしていた |
| ビジュアルリグレッションテスト | コード側の意図しない変化を見つける手段。Figma との突き合わせにはならない |

成熟したチームは、トークンとコンポーネントの層だけを揃え、実装済みの画面はコードを正にしている。これが、調べて分かった一般的な形でした。

## 層ごとに、何を正とするかを決めた

そこで、「画面を同期する」のではなく、**層ごとに防ぐ**ことにしました。

| 層 | 正 | どう防ぐか |
| --- | --- | --- |
| 実装済みの画面 | コード | Figma 側を追従させない。Figma は新しい画面案を検討する場にする |
| 新しい画面案 | Figma | デザインシステムの部品とトークンで組み、最初から食い違いを生まない |
| デザイントークン | Figma のトークンのライブラリ | コードの値と定期的に突き合わせ、ずれていればコードを直す |
| コンポーネント | — | Code Connect は条件を満たしていたが、部品ごとの対応づけの作成と維持に工数がかかるので、今回は見送り |

この方針は、フロントエンドの設計ドキュメントに書きました。「今の画面を Figma に反映して」と頼まれても、エージェントは方針を伝えて止まるようにしています。

### 画面案の起こし方は 3 つを比べた

| 方法 | 仕組み | 評価 |
| --- | --- | --- |
| html.to.design（第三者のプラグイン） | 描画した HTML をレイヤーとして取り込む | 手順が単純。ただし取り込まれるのはただの図形で、デザインシステムの部品と結びつかない。社内の画面を第三者のサービスに送ることになる |
| Figma 公式 MCP の `generate_figma_design`（Code to Canvas） | 同じく HTML を取り込む | 送り先は契約済みの Figma だけ。出力はただの図形 |
| Figma 公式 MCP の `use_figma` ＋ スキル | エージェントが、デザインシステムの部品を使って Figma 上に組み立てる | 部品で組むので、後から直しやすく、食い違いも生みにくい。新しい機能で、品質は未検証 |

部品で組める 3 つ目を選びました。品質が足りなければ 2 つ目に切り替える前提で、1 画面を試してから決めています。試した範囲では、部品を使えたところは十分な品質で、切り替えは要りませんでした。

## トークンの正は、最初は逆に考えていた

最初は、トークンの正を**コード**にしていました。コードのトークンは、移植元の Tailwind の設定から値を移したものです。こちらを正として、Figma をそれに合わせる考えでした。

デザインシステムの担当者に確かめると、**Figma のトークンのライブラリが正**でした。社内の複数のプロダクトで使われているライブラリで、値は今後も変わりえます。正が逆なら、ずれていたときに直す側も逆になります。

そこで、ライブラリの値とコードの値を突き合わせるスクリプトを作りました。初回は 117 件を比べ、対応する 100 件のうち **99 件が一致、1 件が食い違い**でした。残りの 17 件は、コード側で使っていない色の階調や、名前を対応づける対象から外したものです。

| トークン | Figma のライブラリ（正） | コード |
| --- | --- | --- |
| `color/blue/0` | `#f2f8fe` | `#e4f1fd` |

食い違いは、コード側を直します。スクリプトは食い違いがあれば終了コード 1 を返し、0 件の入力は成功扱いにしません（入力の取り違えを「食い違いなし」と読まないため）。

**正は、作った人に確かめるまで決めない。** 移植の経緯からコードを正だと思い込んでいましたが、確かめなければ、正しい値の方を直してしまうところでした。

## 画面案は、正本のブランチに起こす

書き込み先は、正本のファイルの**ブランチ**にしました。デザインチームと次の流れで合意しています。

1. エージェントが、ブランチに画面案を起こす（ブランチは Figma の画面で人が作る。MCP からは作れない）
2. Figma でマージ申請を出し、デザイナーがレビューする
3. デザイナーがマージする

最初は、正本とは別の試し用のファイルに組んでみました。すると、正本で使っている部品の半分ほどが使えませんでした。

- ボタンの部品は、キーを指定しても読み込めなかった
- タブの項目は、非公開の部品だった
- 表の行は、正本のファイルの中だけの部品だった

正本のブランチの中なら、既存の部品のインスタンスを `clone()` すれば、部品として生きたまま使えます。ブランチに書く方針には、この理由もあります。

デザイナーの品質の確認は、試し用の案ではなく、**最初の実案件のマージ申請のレビュー**で行うことにしました。画面案は必ずマージ申請を通るので、採用しない案のために、別の確認の場を作る必要はありません。

### 複製ではなく、元のフレームを直す

既存の画面への変更案は、ブランチの中で**元のフレームを直接直す**ことにしました。

最初は、元の画面を複製して、別のフレームに変更案を起こしていました。すると、マージ申請の確認画面には「追加」としか表示されず、何が変わったのかが見えません。しかも、マージすると正本に同じ画面が 2 つ残ります。

元のフレームを直せば、確認画面は「編集済み」になり、デザイナーが「以前」と「最新」を並べて比べられます。マージすると、正本の画面がそのまま置き換わります。

## use_figma は、読み取り専用にできない

`use_figma` は、Figma のプラグインの API を使う任意のスクリプトを実行できるツールです。ツールの側では、読み取り専用にも、書き込み先の限定にもできません。「正本の本体には書かない」「トークンのライブラリは編集しない」を、手順の約束だけにしたくありませんでした。

そこで、レビューの指摘を受けて、次の 3 つを毎回守ることにしました。

1. **呼ぶ前に、対象と操作を宣言する。** 実行の承認画面にはスクリプトしか出ず、承認する人が対象を読み取りにくいためです

   ```text
   対象: <ファイル名>（ブランチならブランチ名も）
   操作: 読み取りのみ / 書き込み（何を作る・変えるか）
   ```

2. **書き込むスクリプトは、先頭でファイルを確かめる。** 実行中のファイルは `figma.fileKey` で分かります。ブランチではブランチのキーが返るので、許したブランチ以外なら止めます

   ```js
   const ALLOWED_BRANCH = "<ブランチのキー>";
   if (figma.fileKey !== ALLOWED_BRANCH || ["<正本のキー>", "<トークンのライブラリのキー>"].includes(figma.fileKey))
     throw new Error(`書き込み先がブランチではない: ${figma.fileKey}`);
   ```

   承認する人は、この 3 行があることとキーを見て判断できます。正本の本体で止まることも、実際に確かめました

3. **トークンのライブラリには、書き込むスクリプトを実行しない。** 実行してよいのは、手順書にある読み取りのスクリプトだけです

あわせて、Claude Code の設定で、Figma への書き込み系のツールは実行のたびに確認が入るようにしています。

## 実データで分かった落とし穴

手順は、実際の正本で動かして確かめてから、スキルに書いています。踏んだ落とし穴は次のとおりです。

- **部品の検索が、別のプロダクトのライブラリを返す。** `search_design_system` は、自分たちのデザインシステムを返さず、社内の別のプロダクトのライブラリを返しました。部品のキーは、正本の既存の画面から取ります
- **コードとデザインで、バリアントの名前が違う。** コードのボタンの `variant="outline"` は、Figma では `variant=outlined` でした。組み合わせによっては、特定のサイズにしか無いバリアントもあります
- **同じテキストスタイルでも、版によって書体が違う。** 同じ名前・同じキーのスタイルが、版によって Noto Sans JP と Gen Interface JP に分かれていて、同じ画面の中に両方がありました
- **書体が実行環境に無いと、テキストを書き換えられない。** Gen Interface JP は `use_figma` の実行環境に無く、そのテキストは文言を変えられません（`Cannot write to node with unloaded font`）。新しいテキストは Noto Sans JP で作り、スタイルを当てられなかったものは数えて、デザイナーに付け直しを頼みます
- **キーで読み込めない Variable がある。** 正本の画面で使われている Variable が、すべてトークンのライブラリのものとは限りませんでした。キーで読み込めないものは、ブランチの中の既存のノードから ID で取ります

どれも、ドキュメントを読むだけでは気付けないものでした。

## 正本の今を、数字で確かめた

デザイナーから、「Figma で変数になっていない箇所がある」という声がありました。そこで、正本の画面のページ全体（最上位のフレーム 48 個、部品の外のレイヤー 2,616 個）を、読み取りのスクリプトで調べました。

- 色と角丸は、ほとんどが Variable かスタイルに結びついていた
- 余白は、トークンに同じ値があるのに数値を直接指定しているものが、**約 920 か所**あった（削除予定のセクションも含む）

| 余白 | 結びつけるべきトークン | 件数 |
| --- | --- | ---: |
| 8px | `space/8` | 491 |
| 16px | `space/16` | 241 |
| 12px | `space/12` | 84 |
| 32px | `space/32` | 42 |
| ほか（24px・4px・40px） | — | 59 |

デザイナーの感覚を、数字で裏付けた形です。その後、ブランチで機械的に Variable へ結びつけ直し、マージしました。トークンに同じ値があるのに直書きだった余白と黒・白の塗りは、0 件になっています。トークンに無い値の余白などは、デザインの判断が要るので残しました。

途中で、ブランチの作り直しもしています。最初のブランチは、マージを待つ間に正本の変更が進み、競合が増えました。その間に、デザイナー側の作業でも結びつけが進んでいたためです。古いブランチの競合を解くより、今の正本から作り直して残りだけを結びつける方が速く済みました。**ブランチは、待つほど正本から離れていきます。**

なお、この作業は値を変えず、見た目も変わらない機械的なものだったので、デザイナーのレビューは経ずに担当者がマージしました。画面案のように見た目が変わる変更は、これまでどおりデザイナーがレビューしてマージします。

## まとめ

| 決めたこと | 理由 |
| --- | --- |
| 画面は同期せず、層ごとに正を決めた | 画面単位で同期し続ける定番は無く、維持のコストに見合わない |
| トークンの正は Figma のライブラリ。コードと突き合わせる | 作った人に確かめたら、思い込みと逆だった |
| 画面案は、部品で組める `use_figma` で起こす | 最初から食い違いを生まない |
| 書き込み先は正本のブランチ。元のフレームを直す | 正本の中の部品を使え、マージ申請で前後を比べられる |
| 書き込む前にファイルを確かめ、ブランチ以外では止める | `use_figma` は読み取り専用にできない |
| 手順は実データで確かめてから書く | 部品・書体・Variable の落とし穴は、動かして初めて分かった |

学びは 2 つです。

1. **「同期」を諦めると、守る範囲がはっきりする。** 画面ごとの同期は追いかけ続ける作業になります。層ごとに正を決めれば、防ぐのはトークンと部品だけで済みます
2. **AI に書かせる道具は、ツールの外で守りを作る。** 読み取り専用にできない道具は、呼ぶ前の宣言と、スクリプトの先頭の確認で、人が承認できる形にしました
